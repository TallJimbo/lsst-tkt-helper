# Plan: zed-bell plugin for install-opencode-agent

Design approved in conversation (2026-10-14). No separate spec doc. One
implementation task.

## Background / established facts (probed against installed OpenCode v2.0.26)

- OpenCode >= 2.0 autoloads plugins from `<config>/opencode/plugin/` (and
  `plugins/`), but only accepts modules with `export default { id, setup }`
  (or `effect`). Named-export-only modules (the shape of Zed's documented
  snippet) fail with "Plugin must export a default definition with an id and
  an effect or setup function".
- In v2, events reach plugins via `ctx.event.subscribe()`, an async iterable.
  Observed terminal-of-run events on 2.0.26: `session.execution.succeeded` /
  `session.execution.failed`. `session.idle` (v1 spelling) and
  `permission.asked` exist as strings in the 2.0.26 binary; include them for
  cross-generation coverage.
- `opencode acp` sets `OPENCODE_CLIENT=acp`; under ACP stdout is the JSON-RPC
  stream, so the bell write must be skipped there (Zed's snippet guard, kept).
- `harnesses/opencode/plugin/plannotator-wake.js` is the existing
  same-directory precedent: named factory export +
  `export default { id: "tkt-plannotator-wake", setup: PlannotatorWake };`.
- Delivery is a real copied file (plugin loader skips symlinks), done by
  `_install_wake_plugin()` in `tkt/install.py`; `sandbox.py` imports
  `wake_plugin_source` / `wake_plugin_dest` for a staleness warning — those
  two functions must keep working unchanged.

## Task 1: zed-bell plugin + installer generalization + tests + docs

### Files

- Create `harnesses/opencode/plugin/zed-bell.js` — verbatim from this plan:

```js
// harnesses/opencode/plugin/zed-bell.js
// Emits a terminal bell when OpenCode needs attention, so Zed Terminal Threads
// fire their agent notification (pop-up + optional sound; see Zed docs
// ai/terminal-threads.md "OpenCode Notifications"). Zed's documented snippet
// uses the v1 plugin hook shape, which OpenCode >= 2.0 refuses to load
// ("Plugin must export a default definition with an id and an effect or setup
// function"); this keeps the same behavior in the v2 shape and mirrors the
// named-export + default-wrapper convention of plannotator-wake.js. Installed
// by `tkt install-opencode-agent` as a real copied file in
// ~/.config/opencode/plugin/ (the plugin loader skips symlinks).
export const ZedBell = async (ctx) => {
  // Under ACP, stdout is the JSON-RPC stream: a bell byte would corrupt it.
  if (process.env.OPENCODE_CLIENT === "acp") return;
  const bell = () => process.stdout.write("\x07");
  const attention = new Set([
    "session.idle", // v1 spelling (Zed's snippet)
    "session.execution.succeeded", // observed terminal events on 2.0.26
    "session.execution.failed",
    "permission.asked", // permission prompt (present in 2.0.26)
  ]);
  const watch = async () => {
    try {
      for await (const event of ctx.event.subscribe()) {
        if (event && attention.has(event.type)) bell();
      }
    } catch {
      // Broken event stream: no bells, but never crash the plugin host.
    }
  };
  if (typeof ctx?.event?.subscribe === "function") watch();
};

export default { id: "tkt-zed-bell", setup: ZedBell };
```

## Task 2 (2026-10-15): two-half directory plugin (TUI-side bell)

Root cause found after Task 1 shipped: in OpenCode v2 TUI mode, plugins run in
the server process (`opencode serve --stdio`, child of the `opencode` TUI).
Its stdout is the stdio protocol socket to the TUI, not the pty, so the Task 1
single-file server plugin writes `\x07` into the protocol channel and no
terminal ever sees it (verified via /proc fd tables in a live sandbox: TUI on
/dev/pts/8, server fd1 = socket). `--standalone` still uses a private
`serve --stdio` child; only the shared daemon is bypassed.

Design change: convert `harnesses/opencode/plugin/zed-bell.js` into a
directory plugin `harnesses/opencode/plugin/zed-bell/` with:

- `index.js` — trivial server half: `export default { id: "tkt-zed-bell", setup: () => {} };`
  (a discovered directory with no server entrypoint is silently skipped, so
  the server half must exist but must not write to stdout).
- `tui.js` — the bell logic, run in the TUI process whose stdout IS the pty.
  Same `{ id: "tkt-zed-bell-tui", setup(ctx) }` promise shape; events via the
  TUI plugin context `ctx.data.listen(handler)` (or `ctx.data.on(type, ...)`)
  over OpenCodeEvent types; attention set unchanged (session.idle,
  session.execution.succeeded, session.execution.failed, permission.asked);
  bell = process.stdout.write("\x07"). No ACP guard needed (no TUI under ACP).
  Implementer must confirm the context/event surface against
  investigations/opencode-src/packages/plugin/src/tui/{plugin,context}.ts and
  how packages/tui loads tui entrypoints, and keep the never-throw posture.

Installer (`tkt/install.py`): `_install_plugin` must handle directory plugins
(recursive byte-compare for idempotence; replace stale copy) alongside single
files. `PLUGIN_NAMES` becomes ("plannotator-wake.js", "zed-bell") — or an
equivalent (name, kind) structure. Additionally remove the legacy single-file
`zed-bell.js` from the host plugin dir if present (tkt-owned artifact from the
Task 1 install; it would otherwise still load and write bells into the
protocol socket).

Tests: adapt existing zed-bell cases to the directory; both entrypoint files
copied with correct bytes; idempotence; stale-directory replacement (e.g. an
extra file inside the installed dir is removed or reported — pick the simplest
correct behavior: the installed dir must end up byte-equal to the source tree);
legacy `zed-bell.js` removal; wake single-file path unchanged.

Docs: AGENTS.md wording if it implies single files only; plan doc updated (this
section).

Rulings:
- Ruling: implement against the vendored dev-tree TUI plugin API without an
  installed-2.0.26 probe — human partner chose optimism; accepted cost: if
  2.0.26's discovery lacks tui-plugin support, the bell simply does not fire
  until their install catches up (no worse than today).
- Ruling: server half stays a strict no-op — writing bells from the server
  would keep polluting the stdio protocol stream.
