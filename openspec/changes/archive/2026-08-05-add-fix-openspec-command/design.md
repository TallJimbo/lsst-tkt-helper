## Context

`openspec init --tools opencode` writes Claude-Code-oriented skills into
`<project>/.opencode/skills/openspec-*/SKILL.md`. Those files reference tools
that don't exist in OpenCode (`AskUserQuestion` → `question`,
`TodoWrite` → `todowrite`) and include an `allowed-tools` frontmatter key that
OpenCode's loader ignores. A working fix currently lives as a standalone script
at `~/.config/opencode/investigation/scripts/fix-openspec-skills.py`, outside
`tkt`, and is not tied to workspace creation.

The logic is pure, idempotent, and self-contained (only stdlib: `re`, `pathlib`,
`sys`). It needs to be reusable by both a manual CLI command and the `OpenSpec`
tool's `write()` path.

## Goals / Non-Goals

**Goals:**
- Move the fix logic into the existing `tkt/openspec.py` module as a reusable, pure staticmethod on the `OpenSpec` Tool.
- Expose a standalone `tkt fix-openspec [DIR] [--dry-run]` command.
- Auto-run the fix from `OpenSpec.write()` so freshly-installed workspace skills are OpenCode-ready.
- Preserve the script's idempotency and warn-only-on-missing-anchor behavior.

**Non-Goals:**
- No new runtime dependencies.
- No handling of the case where OpenCode has no `question` tool enabled (out of scope; the skill is the spec, the tool gets added later).
- Not removing the standalone script file itself as a task here (done by the user outside this repo, or as a follow-up; the logic is fully relocated into `tkt`).

## Decisions

### 1. Logic lives in `tkt/openspec.py`, entry point is `OpenSpec.fix_skills` staticmethod

The fix logic lives in the existing `tkt/openspec.py` module, not a new file. The public entry point is a `staticmethod` on the `OpenSpec` Tool — e.g. `OpenSpec.fix_skills(directory: str, *, dry_run: bool = False)` — so the manual CLI command and `OpenSpec.write()` both call `OpenSpec.fix_skills(...)` without needing an instance. The working state (`TOOL_RENAMES`, `ALLOWED_TOOLS_RE`, `QUESTION_TOOL_INJECTIONS`) and the helpers (`fix_content`, `apply_injections`, the directory walker) are private module-level constants, functions, and classes (leading underscore) in the same module, alongside the existing `OpenSpec` class.

*Alternative considered:* a dedicated `tkt/fix_openspec.py` module with a plain function. Rejected per user decision — keeping it in `tkt/openspec.py` avoids a new module and lets the `OpenSpec` Tool be the single home for OpenSpec integration; a `staticmethod` lets the standalone command reuse the entry point without constructing a `Tool`.

### 2. CLI command is a thin wrapper, standalone

`tkt fix-openspec [DIR] [--dry-run]` in `_cli.py` simply resolves `DIR` (default `os.curdir`), validates it, and calls `OpenSpec.fix_skills`, mapping "no SKILL.md found" to exit code 2. It does not require `--environment`/`TKT_ENVIRONMENT`.

*Alternative considered:* workspace-aware command using `--ticket/--directory/--environment`. Rejected per user decision — the manual use case is a plain directory, no environment.

### 3. Auto-invoke from `OpenSpec.write()`, always, warn-only

After the existing `openspec init --tools opencode` block in `OpenSpec.write()`, call `OpenSpec.fix_skills(os.path.join(directory, ".opencode", "skills"))`. Run it unconditionally on every `write()` call (including `update`/`upgrade-metapackage` re-invocations) because it is idempotent. Missing anchors are logged via `logging.warning`, never raised.

*Alternative considered:* only running the fix when `openspec init` actually ran. Rejected — `write()` is re-invoked on update paths, and always running an idempotent fix is simpler and safer.

### 4. Rename the injected-anchor machine-specific default

The standalone script's hardcoded default `~/LSST/tkt2/.opencode/skills` is dropped; the CLI default becomes the current directory.

## Risks / Trade-offs

- [Upstream OpenSpec changes the `openspec-explore` anchors] → Injection code warns and skips; a human sees the warning and updates the anchors in `tkt/openspec.py`.
- [Skills are regenerated by `openspec update`, undoing fixes until `tkt` runs again] → Acceptable; `OpenSpec.write()` re-runs the fix on the next `tkt update`. No extra work now.
- [Auto-invoke adds a small amount of work to `new`/`update`] → Negligible; scanning a few skill files is cheap and idempotent.

## Migration Plan

- Add `OpenSpec.fix_skills` staticmethod + private helpers to `tkt/openspec.py`, wire CLI command, update `AGENTS.md`.
- `OpenSpec.write()` calls `OpenSpec.fix_skills` on `<dir>/.opencode/skills/` after `openspec init`.
- Standalone script at `~/.config/opencode/investigation/scripts/fix-openspec-skills.py` becomes redundant; the user can remove it. No rollback risk (module is additive, no existing behavior removed).
